# n8n 工作流开发经验总结

> 本文档总结 "WF-01 每日营业简报" 从设计到上线的完整开发经验，供后续工作流（WF-02~WF-04 及扩展）复用。
> 总结日期: 2026-05-25

---

## 一、整体开发流程（可复用的标准步骤）

### 步骤 1：明确数据需求

1. 确定工作流要回答什么业务问题（如"今天诊所经营得怎么样"）
2. 列出需要的数据字段（如收入、支出、预约数、接诊人数）
3. 对照 [API接口文档-v2.0.md](../03-接口文档/API接口文档-v2.0.md) 确认后端是否已有对应接口
4. 如果接口缺失或字段不足，先走**后端接口开发**（见下方"后端接口开发规范"），再回来搭工作流

### 步骤 2：生成测试数据

1. 通知开发助手在 MySQL 中生成对应模块的测试数据
2. 使用 `--default-character-set=utf8mb4` 避免中文乱码
3. 数据生成后，手动调用一次 Open API 接口，确认返回结构和字段值正确

### 步骤 3：搭建 n8n 工作流骨架

1. **触发节点选择**：
   - 前端调用 → 选 `Webhook` 节点
   - 定时执行 → 选 `Schedule Trigger` 节点
2. **数据获取节点**：`HTTP Request` 调用后端 Open API
3. **格式化节点**：`Code` 节点提取、精简、重命名字段
4. **AI 分析节点**：`AI Agent` 接入 DeepSeek 模型
5. **输出约束节点**：`Structured Output Parser` 强制 JSON 格式
6. **响应节点**：`Respond to Webhook` 或直接由最后一个节点输出

### 步骤 4：联调与问题修复

1. 逐个节点执行，确认每步输出符合预期
2. 遇到错误时对照下方"踩坑速查表"定位
3. 前端接入后，验证嵌套对象显示是否正常

### 步骤 5：清理与归档

1. 删除测试用的临时 SQL / JSON 文件
2. 更新接口文档和工作流文档中的完成状态
3. 将工作流转为子工作流（如需要被其他流程复用）

## 二、后端接口开发规范（Open API）

### 2.1 新增接口 checklist

| 检查项 | 说明 |
|--------|------|
| 路径规范 | `/api/open/clinic/{clinicId}/xxx`，必须与现有接口风格一致 |
| 认证头 | 必须校验 `X-API-Key`，且 Key 关联的诊所 ID 与路径参数一致 |
| 分页 | 列表接口**必须**支持 `page` + `size`，使用 PageHelper |
| 日期参数 | 统一使用 `startDate` / `endDate`（yyyy-MM-dd），不再混用 `startTime` |
| 字段精简 | 只返回工作流真正需要的字段，不要返回元数据（`id`, `created_at` 等如无必要可省略） |
| 返回结构 | 统一 `Result` 包装：`{ code: "200", msg: "请求成功", data: {} }` |

### 2.2 已有接口优化 checklist

| 检查项 | 常见问题 | 修复方案 |
|--------|---------|---------|
| 全量查询 | `selectAll()` 后内存过滤 | 改为 Mapper 动态 SQL + PageHelper |
| 内存分页 | `subList` 或 `stream.limit` | 改为数据库分页 |
| 字段冗余 | 返回 30+ 个字段 | 新建精简方法或字段白名单 |
| 硬编码文本 | `data_limitations` 等 | 清空或移除 |

### 2.3 日期逻辑注意事项

- `/daily-metrics` 默认返回**昨天**数据（`minusDays(1)`）
- 如需查询当天，必须显式传入 `date=yyyy-MM-dd`
- n8n 表达式：`{{ $now.format('yyyy-MM-dd') }}`

## 三、n8n 节点使用规范

### 3.1 节点命名规则

| 节点类型 | 命名规则 | 错误示例 | 正确示例 |
|---------|---------|---------|---------|
| AI Agent | 只能 `A-Za-z0-9_` | `AI 经营分析` | `AI_Analysis` |
| Code | 建议英文，描述功能 | `代码` | `Format_Data` |
| HTTP Request | 描述数据来源 | `HTTP Request` | `Get_Daily_Metrics` |

### 3.2 数据流转规范

```
HTTP Request 输出 → item.json.data（后端 Result 的 data 字段）
Code 节点输入 → $input.all()[0].json
Code 节点输出 → return [{ json: { ... } }]（必须是数组包裹对象）
AI Agent 输入 → 直接引用前序节点的 json 字段
Structured Output Parser → 定义 Schema，字段名用中文方便前端展示
```

### 3.3 Code 节点编写要点

```javascript
// 1. 安全取值：先取 data，如果 data 不存在直接取根级（兼容不同接口）
const item = $input.all()[0].json;
const m = item.data || item;

// 2. 字段映射：统一用英文，不要出现中文键名
return [{
  json: {
    analysis_date: m.analysis_date,      // 正确
    // 分析日期: m.analysis_date,        // 错误！会导致后续节点 undefined
    today_income: m.today_income || 0    // 3. 兜底：数值字段给默认值
  }
}];
```

### 3.4 AI Agent 提示词模板

```text
你是一位口腔诊所经营分析专家。

请根据以下经营数据生成简报：
- 日期: {{ $json.analysis_date }}
- 今日收入: {{ $json.today_income }}
- 今日支出: {{ $json.today_expense }}
- ...（其他字段）

要求：
1. 生成经营评分（0-100）和一句话评分说明
2. 列出核心指标
3. 给出 AI 分析摘要（50-100字）
4. 如有异常，给出风险提示
5. 给出 1-2 条具体建议动作

最终输出必须是纯 JSON，JSON 内部不要包含换行符，使用紧凑格式。
```

### 3.5 Structured Output Parser Schema 设计原则

1. **字段名用中文**：前端直接渲染，用户可读性好
2. **层级不要太深**：最多 2 层嵌套，否则前端处理复杂
3. **每个字段给 description**：帮助模型理解该字段应该填什么
4. **字符串值不要允许换行**：否则 DeepSeek 容易插入 `\n`

示例（推荐）：

```json
{
  "简报日期": { "type": "string", "description": "格式 yyyy-MM-dd" },
  "经营评分": { "type": "number", "description": "0-100 的整数" },
  "核心指标": {
    "type": "object",
    "properties": {
      "今日总收入": { "type": "number" },
      "今日总支出": { "type": "number" },
      "今日净收入": { "type": "number" }
    }
  },
  "AI分析摘要": { "type": "string", "description": "50-100字的经营分析" },
  "建议动作": { "type": "string" }
}
```

## 四、前端适配规范

### 4.1 AI 返回数据解析

AI 返回的数据可能是：
- 纯字符串
- JSON 字符串
- 嵌套 JSON 对象

前端必须做三层兼容处理：

```javascript
extractReplyContent(data) {
  // 1. 如果是字符串，尝试解析 JSON
  if (typeof data === 'string') {
    try { data = JSON.parse(data) } catch (e) {}
  }
  // 2. 如果是对象，优先取常见字段
  if (typeof data === 'object' && data !== null) {
    return data.content || data.reply || data.message || data
  }
  return data
}
```

### 4.2 嵌套对象渲染

当 AI 返回嵌套对象（如 `{ "核心指标": { "今日总收入": 8560 } }`），不能用 `String(obj)`，会输出 `[object Object]`。

必须实现递归转换方法：

```javascript
formatObjectToText(obj, indent = 0) {
  if (obj === null || obj === undefined) return ''
  if (typeof obj !== 'object') return String(obj)
  if (Array.isArray(obj)) {
    return obj.map((item, i) => `${'  '.repeat(indent)}${i + 1}. ${this.formatObjectToText(item, indent + 1)}`).join('\n')
  }
  return Object.entries(obj)
    .map(([k, v]) => `${'  '.repeat(indent)}${k}: ${this.formatObjectToText(v, indent + 1)}`)
    .join('\n')
}
```

### 4.3 JSON 卡片渲染

如果前端使用卡片展示 JSON 数据，值需要根据类型分别渲染：

```javascript
renderJsonCardValue(value) {
  if (value === null || value === undefined) return '-'
  if (typeof value === 'boolean') return value ? '是' : '否'
  if (typeof value !== 'object') return String(value)
  if (Array.isArray(value)) {
    return value.length === 0 ? '-' : value.map(v => this.renderJsonCardValue(v)).join(', ')
  }
  // 对象类型：递归为文本
  return this.formatObjectToText(value, 1)
}
```

## 五、测试数据生成与验证流程

### 5.1 协作模式

1. 用户要测试某个 n8n 工作流时，通知开发助手需要测试哪个接口/工作流
2. 开发助手在 MySQL 数据库中生成对应模块的测试数据
3. 用户在 n8n 中执行工作流，将返回结果复制给开发助手
4. 开发助手根据返回结果判断：数据是否正确、字段是否匹配预期、业务逻辑是否合理
5. 如有问题，开发助手定位原因并修复（后端代码、工作流配置或字段映射）

### 5.2 测试数据生成注意事项

- MySQL 字符集：Docker 中 mysql 客户端默认 latin1，需用 `--default-character-set=utf8mb4` 或通过 SQL 文件导入
- 数据量：每个模块至少 5-10 条，覆盖不同状态/类型（如收入+支出+退款）
- 日期：覆盖今天、昨天、上月，便于测试时间维度接口
- 测试数据用完后及时清理，保持数据库干净

### 5.3 结果验证 checklist

| 验证项 | 通过标准 |
|--------|---------|
| 数据完整性 | 所有预期字段都有值，无 `undefined` |
| 数据正确性 | 数值与数据库实际记录一致（可抽查 1-2 条） |
| 字段名匹配 | n8n Code 节点、AI 提示词、Schema 定义三者字段名一致 |
| JSON 合法性 | Structured Output Parser 不报错，无非法控制字符 |
| 前端显示 | 无 `[object Object]`，嵌套对象可读 |
| 中文正常 | 无乱码，无 `????` |

## 六、踩坑速查表

| 现象 | 根因 | 解决方案 |
|------|------|---------|
| `Custom date key can only contain characters "A-Za-z0-9_"` | AI Agent 节点名含中文或空格 | 改名成纯英文+下划线 |
| Code 节点输出全为 0 / undefined | Code 里用了中文字段名或字段路径错误 | 统一用英文字段名，与 HTTP 返回结构对照 |
| `m 未定义` | Code 节点直接写 `m.xxx` 但未声明 `m` | 先 `const m = item.data \|\| item;` |
| Structured Output Parser 报"非法控制字符" | 从聊天窗口复制 JSON 引入了不可见字符 | 从干净文件复制，或重新手打 |
| DeepSeek 输出 JSON 夹杂换行和空格 | 模型在字符串值中插入 `\\n` | 提示词末尾显式要求"JSON 内部不要包含换行符，紧凑格式" |
| 前端显示 `[object Object]` | AI 返回嵌套对象，直接用 `String()` 转换 | 使用 `formatObjectToText` 递归方法 |
| Webhook 只执行第一个节点 | 节点之间未连线或连线断开 | 检查 n8n 画布连线完整性 |
| 接口返回昨天数据 | `/daily-metrics` 默认 `minusDays(1)` | 显式传 `date={{ $now.format('yyyy-MM-dd') }}` |
| MySQL 中文乱码 | 客户端 latin1 连接 utf8mb4 数据库 | `--default-character-set=utf8mb4` 或通过 SQL 文件导入 |
| 数据日期全是 24 号 | n8n 表达式写错或时区问题 | 检查 `$now` 表达式，确认后端时区配置 |

## 七、后续工作流开发建议

基于 WF-01 的经验，后续 WF-02~WF-04 可直接套用以下模板：

### 7.1 标准工作流模板

```
[Trigger: Webhook / Schedule]
    ↓
[HTTP Request: 获取主数据]
    ↓
[Code: 格式化/提取字段]
    ↓
[AI Agent: DeepSeek，节点名用英文]
    ↓
[Structured Output Parser: 中文字段 Schema]
    ↓
[Respond to Webhook / 输出]
```

### 7.2 多数据源工作流（如 WF-02 明日预告）

```
[Trigger]
    ↓
[HTTP Request: 获取预约列表] → [Code: 提取患者ID列表]
    ↓
[Split In Batches: 逐个患者] → [HTTP Request: 患者详情] → [Code: 汇总]
    ↓
[HTTP Request: 医生排班]
    ↓
[HTTP Request: 耗材预警]
    ↓
[Code: 合并所有数据]
    ↓
[AI Agent]
    ↓
[Structured Output Parser]
    ↓
[输出]
```

### 7.3 关键差异点

| 工作流 | 数据源数量 | 特殊处理 |
|--------|-----------|---------|
| WF-01 每日简报 | 1 个（/daily-metrics） | 字段精简，直接分析 |
| WF-02 明日预告 | 4 个（预约、患者、排班、耗材） | 需批量查询患者详情 |
| WF-03 回访预警 | 1 个（/patients/workbench） | 前端筛选风险标记，无需多接口 |
| WF-04 医生周报 | 3 个（业绩、治疗、预约） | 需按医生分组聚合 |
