# 口腔门诊 SaaS 管理系统 — 二次开发需求文档

> 版本：v1.0  
> 日期：2026-05-06  
> 状态：待评审

---

## 一、背景与目标

本项目为口腔门诊 SaaS 管理系统，涵盖管理后台（桌面端）、患者微信门户、员工微信 H5 三大入口。当前系统已完成核心功能开发并能在本地稳定运行，但在用户体验、部署便捷性、业务逻辑闭环、AI 能力等方面仍有较大提升空间。

**本次二次开发的核心目标：**
1. 修复现有系统的底层数据一致性与业务逻辑缺陷；
2. 引入现代化的 UI 设计语言，提升系统的专业感与高级感；
3. 实现全套 Docker 容器化部署，支持"一键启动"开发/测试/生产环境；
4. 升级 AI 能力，从单一的经营分析扩展为覆盖经营、临床、管理的全场景 AI 助手；
5. 预留标准化的外部 AI Agent 对接入口，支持未来通过 n8n / 阿里云百炼等平台编排的 Agent 能力接入。

## 二、项目现状概述

### 2.1 技术栈
- **前端**：Vue 2.6.14 + Vue Router 3 + Element UI 2.15 + Axios + ECharts + XLSX
- **后端**：Spring Boot 3.2.5 + MyBatis + MySQL 9.6 + Flyway + PageHelper + Lombok
- **构建**：Vue CLI 5（前端）、Maven（后端）
- **AI**：OpenAI Responses API（gpt-5.4-mini），经营日报/周报/月报 + 财务分析对话

### 2.2 已知问题
- **数据一致性**：`appointment`、`medical_records`、`treatment` 等表冗余存储 `patient_name`，患者改名后历史记录不会同步更新；`PatientService.deletePatient()` 级联删除遗漏 `patient_referral_records` 和 `patient_insight_summary`。
- **性能风险**：`PatientMapper` 列表查询使用 correlated subquery 计算 `latest_visit_doctor` 和 `latest_treatment`；`Patient360Controller` 单次请求聚合 10+ 个模块数据，响应体庞大。
- **安全缺陷**：`PatientController` 中二级密码 `"246810"` 硬编码。
- **部署局限**：无 Dockerfile / docker-compose，依赖手动 Shell 脚本部署。
- **UI 风格**：Element UI 默认风格为主，部分页面已引入圆角、渐变等现代元素，但缺乏统一的 Design System。
- **AI 局限**：AI 能力仅集中在经营分析模块，对话 UI 为传统 Element UI 表单样式，未扩展到临床场景；无外部 Agent 对接能力。

## 三、需求详述

### 3.1 方向一：底层修复与数据治理

#### 3.1.1 冗余字段同步机制
- **问题**：子表（`appointment`、`medical_records`、`treatment` 等）冗余存储 `patient_name`，患者改名后产生数据不一致。
- **需求**：
  - 方案 A（推荐）：在 `PatientService.updatePatient()` 中增加级联更新逻辑，同步修改所有关联表中的 `patient_name`。
  - 方案 B（备选）：移除子表 `patient_name` 冗余，查询时通过 JOIN 获取，需评估性能影响。
  - 决策由开发阶段根据数据量评估后确定。

#### 3.1.2 级联删除完整性
- **问题**：`PatientService.deletePatient()` 未清理 `patient_referral_records` 和 `patient_insight_summary`。
- **需求**：补充遗漏表的级联删除；引入 Flyway 迁移脚本清理历史孤儿数据。

#### 3.1.3 Patient360 按需加载
- **问题**：`Patient360Controller` 一次性聚合过多模块，任一子模块异常即整体失败。
- **需求**：
  - 将 Patient360 拆分为多个按需加载的 API（如 `/patient360/basic`、`/patient360/medical-records`、`/patient360/timeline`）。
  - 前端改为分区块异步加载，提升首屏速度与容错性。

#### 3.1.4 安全加固
- **问题**：二级密码硬编码。
- **需求**：将二级密码迁移至 `application.yml` 配置项（环境变量注入），并支持生产环境通过配置中心或数据库动态管理。

---

### 3.2 方向二：Docker 全套容器化部署

#### 3.2.1 目标
实现"一条命令启动完整系统"，兼容本地开发、测试服务器、生产服务器多种环境。

#### 3.2.2 需求清单
1. **前端镜像**：基于 Node 构建阶段 + Nginx 运行阶段的多阶段 Dockerfile，支持通过环境变量注入后端 API 地址。
2. **后端镜像**：基于 Eclipse Temurin JDK 17 的轻量级 Dockerfile，JAR 启动，支持通过环境变量注入数据库、微信、OpenAI 配置。
3. **MySQL 镜像**：基于官方 MySQL 镜像，初始化时自动执行 Flyway 迁移（或由后端启动时执行）。
4. **docker-compose.yml**：
   - 服务编排：frontend、backend、mysql、（可选）nginx 反向代理。
   - 环境配置：通过 `.env` 文件区分 `dev` / `test` / `prod`。
   - 数据持久化：MySQL 数据卷映射，影像上传目录映射。
   - 健康检查：backend 和 mysql 增加 `healthcheck`。
5. **部署脚本**：提供 `deploy.sh` 一键构建、备份、滚动更新。

### 3.3 方向三：UI 现代化改造

#### 3.3.1 设计原则
- **高级感**：大圆角（16-20px）、柔和阴影、微渐变、留白充足、色彩克制。
- **现代感**：卡片化布局、无边界表格、悬浮操作、玻璃拟态（可选）。
- **一致性**：建立 Design Token（颜色、字体、间距、圆角、阴影），所有页面遵循统一规范。

#### 3.3.2 核心页面（第一阶段）
| 页面 | 当前问题 | 优化方向 |
|------|---------|---------|
| **HomeView（首页仪表盘）** | 传统后台统计卡片，信息密度低 | 数据可视化升级（ECharts 现代化）、关键指标 K PI 卡片、今日待办工作台 |
| **Patient360View（患者 360）** | 单页聚合过多模块，加载慢 | 分区块 Tab 化/卡片化、按需加载、时间轴可视化、影像画廊 |
| **BusinessAnalysisView（AI 经营日报）** | Element UI 表单风格对话 UI | ChatGPT/Claude 风格对话界面、Markdown 渲染、代码块高亮、流式输出 |
| **AppointmentView（预约管理）** | 传统表格+表单 | 日历视图 + 卡片列表双模式、拖拽排班、状态颜色语义化 |
| **MedicalRecordView（病历管理）** | 表单密集，可读性差 | 病历时间轴、结构化展示、牙位图形化 |

#### 3.3.3 全局组件升级
- **表格**：统一表头样式、行悬浮效果、空状态插画、加载骨架屏。
- **表单**：统一输入框圆角、Label 顶部对齐（减少横向空间占用）、错误提示动画。
- **弹窗/抽屉**：统一圆角、阴影层级、过渡动画。
- **导航**：侧边栏支持折叠图标模式、当前项高亮、徽标红点。

#### 3.3.4 执行策略
- 先建立 Design System（Token + 基础组件覆写），再逐步迁移各页面。
- 新旧页面可共存，按模块逐个替换，避免一次性全量重构带来的风险。

### 3.4 方向四：业务逻辑闭环优化

#### 3.4.1 预约 → 病历 → 处置 → 收费 业务流
- **现状**：各模块数据独立录入，存在重复输入患者信息、手动关联的情况。
- **优化方向**：
  - **快捷流转**：在预约列表中直接"开始就诊"，自动带入患者信息生成待填写病历；病历保存后自动创建对应处置记录；处置确认后一键生成收费单。
  - **状态联动**：预约状态（已到诊/已治疗/已收费）与病历、处置、收费单实时联动，避免信息孤岛。
  - **智能提醒**：预约到达前 30 分钟系统提醒；处置完成后未生成收费单，提醒医生补录。

#### 3.4.2 耗材/义齿加工供应链联动
- **现状**：耗材采购、库存、义齿订单、账单为独立模块，缺少联动。
- **优化方向**：
  - 病历中开具的义齿加工单自动同步至技工订单模块；
  - 技工账单确认后，自动扣减关联耗材库存（如需要）；
  - 耗材库存低于安全线时，自动提醒采购。

#### 3.4.3 患者全生命周期管理
- **优化方向**：
  - 患者时间轴（PatientTimeline）整合咨询、预约、就诊、收费、随访、影像等全量事件；
  - 患者标签与分组支持智能规则（如"最近 3 个月未复诊"自动打标签）；
  - 转诊记录与咨询来源打通，形成完整的获客链路追踪。

### 3.5 方向五：AI 全场景助手升级

#### 3.5.1 AI 对话 UI 现代化
- **需求**：将现有的 AI 财务分析对话界面重构为类 ChatGPT/Claude 的现代化对话 UI。
- **具体功能**：
  - 左侧会话历史列表（支持新建会话、删除、重命名）；
  - 右侧对话区域：用户消息（右侧气泡）、AI 消息（左侧卡片）、支持 Markdown 渲染、表格、代码块；
  - 流式打字机效果（SSE 实时输出）；
  - 快捷问题推荐（底部预设问题胶囊）；
  - 支持上传文件/图片进行 AI 分析（如上传影像让 AI 辅助描述）。

#### 3.5.2 扩展 AI 场景
| 场景 | 功能描述 | 接入点 |
|------|---------|--------|
| **AI 病历摘要** | 根据病历内容自动生成结构化摘要（主诉、诊断、治疗计划） | 病历详情页 / 病历编辑页 |
| **AI 智能随访建议** | 根据患者病历和就诊历史，生成个性化随访话术和回访时间建议 | 随访管理页 |
| **AI 预约提醒文案** | 根据患者预约项目，自动生成微信/短信提醒文案 | 预约列表页 |
| **AI 经营洞察问答** | 自然语言查询经营数据（"上周哪个医生的业绩最高？"） | AI 经营日报页 |
| **AI 患者风险评估** | 根据病历、影像、病史自动标记高风险患者并给出关注建议 | 患者 360 视图 |

#### 3.5.3 技术方案
- 复用现有 `BusinessAnalysisChatService` 的会话管理和长期记忆机制；
- 各场景通过不同的 System Prompt 调用同一底层 LLM 服务（或针对不同场景配置不同模型）；
- 引入 Function Calling / Tool Use 能力，让 AI 能调用后端 API 查询实时数据。

### 3.6 方向六：外部 AI Agent 统一入口

#### 3.6.1 需求背景
用户计划未来在 n8n 或阿里云百炼等平台编排多个 AI Agent（如智能客服 Agent、智能排班 Agent、智能营销 Agent 等），需要在本系统内提供统一入口来调用这些外部 Agent。

#### 3.6.2 功能需求
1. **AI Agent 中心页面**：
   - 展示已配置的所有外部 Agent 列表（图标、名称、描述、状态）；
   - 每个 Agent 点击进入独立的对话/操作界面；
   - 支持管理员在后台配置 Agent 的接入参数（名称、API 地址、认证密钥、图标等）。
2. **标准化对接层**：
   - 后端提供统一的 `ExternalAgentService`，封装对外部 Agent 的调用；
   - 支持 HTTP API、Webhook、SSE 流式响应等多种协议；
   - 请求/响应日志记录与异常熔断机制。
3. **前端嵌入方案**：
   - 独立页面模式：每个 Agent 一个全屏对话页面（类似 3.5.1 的对话 UI）；
   - 浮动窗口模式：右下角悬浮球，点击展开 Agent 选择器 + 快捷对话。
4. **扩展性**：
   - 新增 Agent 仅需在数据库配置一条记录，无需修改代码；
   - 预留 SDK 接入能力（如阿里云百炼的 JS SDK）。

#### 3.6.3 数据模型（预留）
```
external_agent_config
  - id, name, description, icon_url
  - endpoint_url, auth_type, auth_token
  - protocol (http_api / webhook / sse / sdk)
  - input_schema, output_schema
  - enabled, created_at, updated_at
```

## 四、分阶段执行计划

基于"先稳定底层，再升级体验，最后扩展智能"的原则，建议按以下阶段推进：

### 阶段一：基础修复 + Docker 化（预计 1-2 周）
- **目标**：让系统具备稳定的开发/部署基座。
- **内容**：
  1. Docker 全套容器化（前端、后端、MySQL、docker-compose）。
  2. 数据一致性修复：`patient_name` 级联更新、级联删除补全。
  3. Patient360 按需加载拆分。
  4. 二级密码外置配置。
- **交付物**：
  - `Dockerfile`（前端 + 后端）
  - `docker-compose.yml`（dev / test / prod 三环境）
  - 数据修复 Flyway 脚本
  - 部署文档

### 阶段二：UI Design System + 核心页面升级（预计 2-3 周）
- **目标**：建立统一设计规范，完成高频核心页面的视觉升级。
- **内容**：
  1. 建立 Design Token 和基础组件库（颜色、字体、间距、按钮、表单、表格、弹窗）。
  2. 重写 HomeView（仪表盘）、Patient360View（患者 360）、AppointmentView（预约管理）。
  3. MedicalRecordView（病历管理）结构化展示升级。
- **交付物**：
  - `design-system.md` 设计规范文档
  - 5 个核心页面 Vue 代码
  - 全局样式文件更新

### 阶段三：业务闭环 + AI 场景扩展（预计 2-3 周）
- **目标**：打通核心业务流，让 AI 能力覆盖更多场景。

  1. 预约→病历→处置→收费快捷流转。

  - 业务流转 API 和前端交互
  - AI 对话组件（独立可复用）
  - 各场景 AI Prompt 和 Function Calling 配置

### 阶段四：外部 AI Agent 中心（预计 1 周）
- **目标**：预留标准化外部 Agent 对接能力。
- **内容**：
  1. `external_agent_config` 数据表和 CRUD 管理后台。
  2. `ExternalAgentService` 统一对接层。
  3. AI Agent 中心前端页面（列表 + 独立对话页 + 悬浮窗）。
  4. n8n Webhook 和阿里云百炼 API 的接入示例文档。
- **交付物**：
  - Agent 配置管理页面
  - Agent 对话组件（复用阶段三的 Chat UI）
  - 接入示例文档（n8n + 百炼）

### 阶段五：回归测试与性能优化（预计 1 周）
- **目标**：确保所有改动稳定、无回归。
- **内容**：
  1. 核心业务流端到端测试（患者→预约→病历→收费）。
  2. AI 对话功能测试（流式输出、Function Calling、会话保持）。

## 六、风险与依赖

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Vue 2 生命周期限制 | Element UI + Vue 2 升级现代 UI 天花板明显 | 在现有框架内最大化改造；如需突破天花板，需评估 Vue 3 迁移成本（不在本次范围） |
| AI 接口成本与稳定性 | OpenAI / 百炼 API 调用存在费用和可用性风险 | 设计熔断降级机制（API 不可用时回退到规则分析或友好提示）；提供开关控制 |
| 数据迁移风险 | patient_name 级联更新涉及多张大表，可能锁表 | 在低峰期执行；小数据量直接 UPDATE，大数据量分批处理或改 JOIN 方案 |
| 外部 Agent 接口未确定 | n8n / 百炼 Agent 尚未搭建，接口格式未知 | 先设计通用抽象层，通过 Mock 接口验证前端；Agent 实际搭建后只需配置参数 |
| 业务逻辑耦合度高 | Treatment→Appointment 自动同步等逻辑修改易引入 bug | 每次修改后跑通核心流程 E2E 测试；小步快跑，每改动一个点即验证 |

## 七、待决策事项

以下事项需在开发启动前或对应阶段启动前确认：

1. **patient_name 冗余处理方案**：选择级联更新（保持冗余）还是移除冗余改 JOIN（影响性能）？
2. **Vue 2 框架限制**：是否接受在 Vue 2 框架内做最大努力改造，暂不升级到 Vue 3？
3. **AI 模型选择**：全场景 AI 助手继续使用 OpenAI，还是迁移到国内模型（通义千问、文心一言）以降低成本？
4. **外部 Agent 首批接入**：第一个接入的外部 Agent 计划使用 n8n 还是阿里云百炼？功能定位是什么？
5. **部署目标服务器**：生产环境预计使用什么配置的云服务器？这影响 docker-compose 的资源限制配置。
