# 阶段五：回归测试与性能优化

> 目标：确保前四个阶段的所有改动稳定运行，核心业务流无回归，性能达到可接受水平
> 预计工期：1 周
> 前置条件：阶段一到阶段四全部开发完成并合并到主干

---

## 一、任务清单

### 1.1 端到端业务流测试

#### 1.1.1 核心流程验证
- **测试路径**：患者注册 → 新增预约 → 到诊 → 书写病历 → 创建处置 → 生成收费单 → 收费完成
- **验证点**：
  1. 患者新增后，患者列表可立即搜索到
  2. 为患者新增预约，AppointmentView 日历/列表中正确显示
  3. 点击"开始就诊"跳转病历新增页，患者信息自动填充
  4. 病历保存后，预约状态自动变为"已到诊"
  5. 病历中勾选"同时创建处置"，处置列表出现对应记录
  6. 处置记录点击"生成收费单"，收费单弹窗数据正确
  7. 收费单保存后，处置状态变为"已收费"
  8. 患者 360 视图的时间轴中按顺序展示以上所有事件
  9. 删除患者后，所有关联数据（预约、病历、处置、收费、随访、影像）一并清除，无孤儿数据

#### 1.1.2 边界场景测试
| 场景 | 预期结果 |
|------|---------|
| 新增患者时手机号重复 | 后端返回明确错误，前端提示"该手机号已存在" |
| 预约时间冲突（同一医生同一时段） | 系统允许或根据业务规则提示冲突 |
| 病历保存后刷新页面 | 数据不丢失，重新加载后展示最新内容 |
| 处置生成收费单后修改金额 | 收费单可正常编辑，处置状态保持"已收费" |
| 删除已收费的患者 | 收费记录随患者一并删除，财务统计不受影响（或标记为删除态） |
| 网络中断后重新连接 | 离线队列中的数据自动同步（复用现有 `initOfflineSync` 机制） |

#### 1.1.3 权限测试
- **admin 账号**：可访问所有页面，可配置 AI Agent，可操作患者删除
- **doctor 账号**：可查看/编辑自己负责的病历和处置，不可删除患者
- **nurse 账号**：可新增/编辑预约，可查看病历但不可编辑
- **测试方法**：使用不同角色账号登录，逐一验证菜单可见性和操作权限

### 1.2 AI 功能测试

#### 1.2.1 AI 经营日报
- **测试内容**：
  1. 点击"生成今日日报"，5 秒内返回结果（或流式输出在 10 秒内完成）
  2. 日报内容包含 headline、summary、risks、opportunities、actions 五个字段
  3. 对话功能：发送"本周收入趋势"，AI 返回数据并附带 ECharts 迷你图
  4. 会话历史：新建会话 → 发送消息 → 切换会话 → 返回后历史消息保留
  5. 网络断开测试：断开 WiFi 后发送消息，前端显示网络错误提示，恢复后可重试

#### 1.2.2 AI 病历摘要
- **测试内容**：
  1. 选择一份完整病历，点击"生成 AI 摘要"
  2. 摘要内容结构化，包含主诉、诊断、治疗计划、医嘱
  3. 摘要生成时间 < 5s
  4. 空病历（仅有患者信息无内容）点击生成，AI 返回"病历内容不足，无法生成摘要"

#### 1.2.3 AI 随访建议
- **测试内容**：
  1. 选择一位有近期治疗记录的患者，获取 AI 随访建议
  2. 建议包含：建议随访时间、随访话术、关注要点
  3. 点击"应用到表单"，新增随访页面的时间和内容自动填充

#### 1.2.4 AI 患者风险评估
- **测试内容**：
  1. 在 Patient360 查看不同风险等级的患者（低风险/中风险/高风险）
  2. 徽章颜色正确（绿/橙/红）
  3. 点击展开后，评估报告内容合理，无幻觉信息
  4. 新增病历后，风险等级异步更新

#### 1.2.5 外部 AI Agent 测试
- **测试内容**：
  1. 配置一个 Mock Agent（指向本地测试服务），测试连接成功
  2. 发送消息，正常接收响应
  3. 关闭 Mock Agent 服务，前端显示"Agent 离线"，不崩溃
  4. SSE 协议 Agent 测试流式输出正常

### 1.3 Docker 部署验证

#### 1.3.1 本地开发环境
- **验证步骤**：
  1. 克隆项目到全新目录
  2. 执行 `cp .env.example .env`
  3. 执行 `docker-compose up -d`
  4. 3 分钟内访问 `http://localhost:7070` 正常显示登录页
  5. 使用 admin/admin123 登录成功
  6. 新增患者、新增预约、新增病历各一次，数据正常保存
  7. 执行 `docker-compose down`，再 `docker-compose up -d`，确认数据不丢失

#### 1.3.2 生产环境模拟
- **验证步骤**：
  1. 使用 `.env.prod` 配置（关闭 Flyway clean、启用更严格的日志级别）
  2. 构建镜像体积检查：前端镜像 < 50MB，后端镜像 < 200MB
  3. 健康检查验证：`docker-compose ps` 显示所有服务 `healthy`
  4. 日志检查：`docker logs clinic-backend` 无 ERROR 级别异常
  5. 资源限制验证：docker-compose 中设置 `mem_limit`，确认服务在限制内正常运行

### 1.4 性能基准测试

#### 1.4.1 前端性能
- **测试工具**：Chrome DevTools Lighthouse
- **测试页面**：HomeView、Patient360View、AppointmentView
- **目标指标**：
  | 指标 | 目标值 |
  |------|--------|
  | 首屏加载时间 (FCP) | < 1.5s |
  | 可交互时间 (TTI) | < 3s |
  | Lighthouse Performance 分数 | >= 70 |
  | JS 包体积（gzip） | < 500KB |

#### 1.4.2 后端性能
- **测试工具**：JMeter 或 k6（或简单的 `ab` / `curl` 脚本）
- **测试接口**：
  - `GET /patient360/{id}/basic` — 目标：P95 < 200ms
  - `GET /appointments/selectAll` — 目标：P95 < 300ms
  - `POST /ai/summarize-medical-record` — 目标：P95 < 5s（受 LLM 延迟影响）
  - `GET /external-agents/{id}/chat` — 目标：P95 < 3s（非流式）
- **并发测试**：50 并发用户，持续 5 分钟，错误率 < 1%

#### 1.4.3 数据库性能
- **测试内容**：
  1. `PatientMapper.selectAll()` 在 1000 条患者数据下的查询时间 < 500ms
  2. `PatientMapper` 的 correlated subquery（`latest_visit_doctor`、`latest_treatment`）在 5000 条数据下的查询时间 < 1s
  3. 若超时，记录为性能债，建议后续增加索引或优化为 JOIN

### 1.5 安全测试

#### 1.5.1 输入校验
- **测试内容**：
  1. SQL 注入：在患者姓名、病历主诉等输入框输入 `' OR 1=1 --`，确认系统不报错且数据不泄露
  2. XSS：输入 `<script>alert(1)</script>`，确认前端不执行脚本，后端存储时转义
  3. 文件上传：上传非图片文件到影像上传接口，确认被拒绝；上传大文件（> 200MB），确认被拦截

#### 1.5.2 鉴权测试
- **测试内容**：
  1. 未登录直接访问 `/BusinessAnalysis`，确认重定向到登录页
  2. 使用 nurse 账号访问 `/SystemAccountPermission`，确认返回 403
  3. 尝试删除 Patient 接口不传二级密码，确认返回 403
  4. 修改前端路由直接访问 `/patient360/1`，确认只能看到自己有权限的患者

#### 1.5.3 配置安全
- **测试内容**：
  1. `application.yml` 中的 `api-key`、`auth-token` 未硬编码，通过环境变量注入
  2. `.env` 文件在 `.gitignore` 中，不会提交到版本库
  3. Docker 镜像中无源码或敏感配置文件残留（多阶段构建）

## 四、风险与注意事项

1. **AI 接口成本**：性能测试中频繁调用 LLM 接口可能产生费用，建议：
   - 使用本地 Mock 服务替代真实 LLM 进行并发测试
   - 真实 LLM 测试仅执行少量单线程验证
2. **测试环境隔离**：性能测试应在独立的 Docker 环境中进行，避免影响开发/生产数据库
3. **数据准备**：端到端测试需要准备测试数据集（患者、医生、预约、病历各 50+ 条），建议编写 `test-data.sql`
4. **浏览器兼容性**：前端测试以 Chrome 为主，若需支持 Safari/Firefox/Edge，需额外增加测试时间
5. **回归范围**：阶段一到四的改动涉及约 50+ 个文件，回归测试必须覆盖所有被修改的 Controller 和 Vue 页面
