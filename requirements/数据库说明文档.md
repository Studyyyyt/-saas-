# 口腔门诊 SaaS 数据库说明文档

> 数据库名：`clinic_system`  
> 字符集：`utf8mb4`（支持 Emoji 和中文生僻字）  
> 存储引擎：`InnoDB`  
> 表总数：53 张（不含 Flyway 迁移历史表）  
> 导出日期：2026-05-06

---

## 一、初始化方式

### 方式一：Docker MySQL 首次启动自动导入
将 `schema.sql` 和 `seed.sql` 放入 MySQL 容器的初始化目录：
```yaml
# docker-compose.yml 中 mysql 服务配置
services:
  mysql:
    image: mysql:8.0
    volumes:
      - ./requirements/schema.sql:/docker-entrypoint-initdb.d/01-schema.sql
      - ./requirements/seed.sql:/docker-entrypoint-initdb.d/02-seed.sql
      - mysql_data:/var/lib/mysql
```
MySQL 首次启动时会按文件名顺序（01 → 02）自动执行这两个 SQL 文件。

### 方式二：手动导入
```bash
# 1. 创建数据库
mysql -u root -p -e "CREATE DATABASE clinic_system CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# 2. 导入结构
mysql -u root -p clinic_system < requirements/schema.sql

# 3. 导入基础数据
mysql -u root -p clinic_system < requirements/seed.sql

# 4. 启动后端，Flyway 会自动执行 V33+ 的新迁移脚本
```

### 方式三：由后端 Flyway 自动管理（推荐开发环境）
- 不手动导入 `schema.sql`
- 启动后端服务时，Flyway 会自动按 V1 → V32 的顺序执行所有迁移脚本创建表结构
- 然后执行 `seed.sql` 插入基础数据
- 后续新功能通过新增 `V33__xxx.sql` / `V34__xxx.java` 进行迭代

## 三、核心数据关系

```
patients (患者主表)
├── 1:N → appointment (预约)
├── 1:N → medical_records (病历)
├── 1:N → treatment (处置)
├── 1:N → finances (财务)
├── 1:N → patient_followup (随访)
├── 1:N → patient_timeline (时间轴)
├── 1:N → patient_images (影像)
├── 1:N → patient_consent (知情同意)
├── 1:N → patient_risk_tag (风险标签)
├── 1:N → lab_orders (技工订单)
├── 1:1 → patient_insight_summary (AI 洞察)
└── 1:N → patient_referral_records (转诊)

medical_records (病历)
├── 1:N → medical_record_operations (诊疗操作项)
└── 1:N → treatment (处置，通过 medical_record_id 关联)

treatment_catalog (治疗项目)
└── 1:N → treatment (处置，通过项目名称/ID 关联)

material_categories (耗材分类)
└── 1:N → materials (耗材档案)

material_purchases (采购单)
└── 1:N → material_purchase_items (采购明细)

lab_factories (加工厂)
├── 1:N → lab_factory_products (产品目录)
├── 1:N → lab_orders (技工订单)
└── 1:N → lab_bills (月度账单)

lab_bills (账单)
├── 1:N → lab_bill_items (账单明细)
└── 1:N → lab_bill_unmatched_orders (未匹配订单)
```

## 四、关键设计说明

### 4.1 关联方式
- **无数据库级外键约束**：项目采用逻辑外键（`patient_id`），未设置 `FOREIGN KEY` 约束。
- **冗余存储 `patient_name`**：`appointment`、`medical_records`、`treatment`、`finances` 等子表同时存储 `patient_id` 和 `patient_name`，用于避免频繁 JOIN 查询。
- **风险**：患者改名后，子表中的 `patient_name` 不会自动同步（已在阶段一需求中规划修复）。

### 4.2 时间戳规范
- 所有业务表均包含 `created_at` 和 `updated_at` 字段：
  - `created_at`：`DEFAULT CURRENT_TIMESTAMP`
  - `updated_at`：`DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`

### 4.3 主键策略
- 所有表使用 `BIGINT AUTO_INCREMENT` 作为主键（`users` 表为 `INT`，历史原因）。

### 4.4 索引策略
- 主键均为 `PRIMARY KEY`
- 高频查询字段已建立普通索引（如 `patient_id`、`appointment_date`、`status` 等）
- 部分表建立了联合索引（如 `advertising_spending` 的 `(platform, start_date)`）

### 4.5 敏感数据
- `users.password`：当前为明文存储（`admin123`），**强烈建议**后续升级为 BCrypt 加密
- `patients.phone`：患者手机号未加密存储，生产环境建议脱敏或加密
